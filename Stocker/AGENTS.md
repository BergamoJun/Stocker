## Development conventions

- Product alignment (2026-11-09 user clarification): the normal path must run from ticker input through automatic multidimensional analysis and report generation without requiring user-written article interpretations. Human review is optional correction, evaluation labeling and quality audit. Data collection, review forms and report composition alone do not complete the planned ResearchEngine/RiskCritic. Preserve old review contracts/receipts and use a separately versioned model-analysis contract; never relabel model output as human verification. Preserve source-use gates, deterministic numeric calculations, unvalidated-score withholding and existing scheduled jobs.
- Prefer small interfaces (`SourceAdapter`, `InstrumentResolver`, `MetricEngine`, `ResearchEngine`, `ReportValidator`).
- Distinguish `as_of` (point-in-time cutoff), `published_at`, `retrieved_at`, `effective_period`, and data `currency`.
- Use UTC internally, explicit exchange timezone in UI, ISO-8601 dates/times and decimal-safe calculations for money when appropriate.
- Preserve inputs, data snapshots/hashes, model name, prompt version, code revision, calculation outputs and validator findings for reproducibility.
- Fail closed on unknown ticker identity, invalid symbol mapping, stale critical data and unsupported claims. Surface a partial report with limitations when safe.
- Write Korean result reports for a new reader without investment or project background. Explain what was evaluated, what data was used, what the result means, why it passed or was withheld, and the next check. Define technical terms and units on first use; keep internal English codes in JSON. Separate calculated scenarios, synthetic tests and observed real-market results. Prefer concise explanations over unexplained numbers or status labels.
- Check applicable project code tests before finishing changes, and state which tests were/weren't run.
