# 공유 주식 API 요청 큐

현재 적용 경로는 `extensions.queued_news`다. 기존 메타데이터 정규화·캐시·기업별 보관과 보고서는 재사용하고, 회사 뉴스 전송의 로컬 잠금 획득만 새 큐를 거친다.

```powershell
.\.venv\Scripts\python.exe -B -m extensions.queued_news --baseline <runtime.step2.json> --check --replay
.\.venv\Scripts\python.exe -B -m extensions.queued_news --baseline <runtime.step2.json> --ciks 1664703 789019 2115436
```

새 협력 클라이언트끼리는 현재 가격→뉴스→대량 수집 순서와 같은 순위의 접수 순서를 사용한다. 오래 기다린 요청의 순위도 점진적으로 높인다. 현재 실제 연결한 것은 회사 뉴스 경로이고, 가격·대량 수집 경로의 큐 채택은 후속 연결이다. 기존 동작 중인 과거 수집기는 이 우선순위 큐를 읽지 않는다. 같은 기존 `request.lock`과 `budget.json`을 공유하므로 동시 HTTP 호출·요청 간격·429 대기는 공동으로 준수한다.

이전 운영 도구는 프로젝트 해시를 매번 검사한 뒤 잠금을 시도해, 매우 짧은 해제 구간을 놓칠 수 있었다. 새 경로는 진입 전 무결성 검사를 한 뒤 로컬 잠금만 최대 45초 동안 짧은 주기로 기다리고, 획득 후와 실제 HTTP 직전에 다시 무결성을 검사한다. 잠금을 획득한 요청은 기존과 같이 앞선 완료부터 최소 15초 간격을 확보한다. 따라서 45초는 잠금 대기 구간이며 HTTP와 계정 간격 대기까지 포함한 전체 실행 상한이 아니다.

BE 관찰이 실제 실행 잠금을 보유하면 새 요청을 양보한다. 이미 시작된 요청의 선점·취소나 구버전 작업 전체에 대한 절대 우선순위를 보장하지 않는다. 관찰 파일을 삭제하거나 기존 계산·예약·키를 변경하지 않는다. 기존 수집기가 공유 잠금으로 대기하면 원래 중단/재개 규칙으로 다음 실행 기회에서 이어간다.

큐 상태는 계정 저장소의 `request_queue/tickets/`, 변경 이력은 `request_queue/events/`에 남는다. HTTP 실패·429는 이 계층에서 재시도하지 않으며, 요청 전 대기·실패 캐시의 원래 시각도 유지한다. 요청 수는 실제 HTTP에 대해서만 증가한다. 인스턴스당 회사 뉴스 최대 3회이고 유료 플랜·추가 키·외부 LLM·주문을 사용하지 않는다.
